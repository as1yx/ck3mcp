# CK3 Autonomous Agent 开发任务书

版本：v1.0（开发起点）<br>
编制日期：2026-10-31<br>
目标平台：Windows<br>
文档性质：需求与建议验收基线，不代表相关能力已经实现或实测通过。

## 1. 项目目标

开发一个能通过正常游戏界面操作《Crusader Kings III》的本地 AI Agent。最终目标是在用户启动并选择目标后，持续管理一个王朝，处理内政、外交、战争、事件和继承，直到目标完成、游戏结束或达到停止条件。

第一版交付目标：在固定运行环境与指定测试存档中，自主完成有限的内政操作和普通事件处理，形成“观察—决策—执行—核验—记录”的可靠闭环，并具备连续运行、预算限制和安全停止能力。

用户负责安装正版游戏、提供模型访问方式、载入测试存档及启动 Agent；运行期间不要求用户逐步批准游戏操作。遇到无法可靠处理的问题时，Agent 停止并报告，不以无限重试代替恢复。

## 2. 第一版范围

### 2.1 必须实现

- 识别并绑定已运行、已载入存档的 CK3 窗口。
- 检查运行环境、截图可用性、窗口焦点和暂停状态。
- 读取完成当前任务所必需的界面信息；允许视觉识别，结构化数据接入以可行性验证结果为准。
- 执行内阁任命、建筑入队、婚约请求和已列入支持清单的普通事件选择。
- 为每类操作实现明确的前置条件与结果核验。
- 在暂停与有限推进游戏时间之间循环，持续处理支持范围内的任务。
- 保存决策摘要、操作证据、错误、预算消耗及运行状态。
- 提供人工紧急停止、自动停止、测试存档备份和运行报告。
- 支持重新启动后核对当前局面，再由用户显式恢复运行。

### 2.2 第一版不承诺

- 从启动器开始自动登录、启动游戏、创建角色或加载任意存档。
- 完整战争指挥、复杂继承规划、所有政体及所有 DLC 的适配。
- 任意分辨率、语言、缩放、全屏模式或多显示器布局下通用。
- 游戏崩溃后自动重启并续玩。
- 铁人、成就、多人模式或同时操作多个王朝。
- 无人值守完成整局、统一指定区域或保持长期最优策略。

### 2.3 操作边界

- 第一版通过正常游戏 UI 改变游戏状态，不使用作弊控制台、内存写入或 Mod 指令直接授予资源、头衔、婚姻与战争结果。
- 可行性实验中的只读遥测 Mod 必须独立说明其影响；不得把读取数据成功表述为动作执行成功。
- 默认只允许利用玩家正常可见的信息。若遥测包含隐藏信息，必须过滤或另设明确的实验模式，报告中注明。
- 默认运行时独占游戏输入；用户操作电脑或游戏失去焦点时，Agent 停止新增输入，不自动抢回焦点。

## 3. 固定测试环境

开工时记录实际环境，禁止根据本文推测用户机器配置。配置缺失时，先检查可读取的信息，再集中询问剩余必要信息。

必须记录：

- Windows 版本与构建号。
- CK3 安装渠道、版本、校验信息（可获得时）、可执行文件位置。
- DLC、Mod 与游戏规则清单。
- 游戏语言、分辨率、Windows 显示缩放、游戏 UI 缩放。
- 窗口模式、显示器和截图区域。
- 测试存档名称、文件哈希、起始日期、角色和必要前置状态。
- Python 版本、依赖锁定文件、Agent 代码版本。
- 模型服务、模型标识、超时、调用预算和计价配置（若使用费用预算）。

建议首次测试采用单显示器、固定分辨率和窗口化或无边框模式；具体值以用户现有环境和实测结果为准。环境改变后重新校准，不能继续使用旧截图坐标。

测试使用非铁人单人存档副本。保留只读基线副本，运行产生的存档与基线分离。

## 4. 开工可行性验证（阶段 0）

先完成以下实验，再确定最终底层依赖和第一版实施范围。

### 4.1 游戏内截图和输入

1. 连续获取 CK3 客户区截图，检查黑屏、遮挡、缩放和坐标偏移。
2. 验证点击、右键、悬停提示、滚动、按键和暂停控制。
3. 验证窗口移动、失焦和弹窗出现后不会沿用旧坐标。
4. 验证模型请求未返回时，紧急停止仍然生效。
5. 记录真实游戏内结果；记事本测试仅用于初步检查，不替代 CK3 验证。

### 4.2 结构化状态读取

用最小只读 Mod 实验验证：当前 Windows 与 CK3 版本能否导出游戏日期、当前角色、金币、收入和继承人等字段。

记录导出触发方式、刷新频率、暂停时是否可更新、日志路径、编码、截断或轮转行为，以及数据是否来自同一次采样。测试跨存档加载后旧日志是否可能误用。

如果不通过，保留视觉方案，缩小可可靠识别的字段和任务范围；不得编造缺失状态或将 Mod 支持写成已实现。

### 4.3 现成代码复用

候选依赖只用于评估，不预设必须采用。检查许可证、安装方式、截图与输入模块的独立性、停止机制和维护成本；采用时固定提交或发布版本。

优先复用确定性的截图、输入和日志能力。第一版只保留一个负责决策与调度的 Runner，不直接将另一个完整自主 Agent 的无限循环嵌入其中。

阶段产物：环境清单、实验记录、采用/不采用的依赖及理由、已确认限制。实验失败时提交具体证据和可行替代路线。

## 5. 系统结构

建议使用 Python 开发。MCP 是工具适配层，不承担长期调度本身；核心控制模块应能被本地 Runner 直接调用，也能通过 MCP 暴露受限接口。

1. **观察模块**：截图、文字与界面识别、可选的只读日志解析。
2. **状态模块**：统一字段、来源、时间戳、有效性与未知状态。
3. **决策模块**：在支持的任务中选择目标，输出结构化行动计划与简短理由。
4. **执行模块**：检查前置条件，执行短小动作，核验结果。
5. **运行器**：串行调度、暂停与时间推进、预算、重试、停止和恢复。
6. **记录模块**：运行日志、决策摘要、截图证据、结果与存档关联。

模型负责理解和选择；窗口边界检查、参数校验、预算和停止由本地程序强制执行。模型返回的内容不允许直接作为任意 Python、Shell 或系统命令运行。

## 6. 状态与动作约定

### 6.1 观察结果

每次观察应包含：

- `observation_id`、运行 ID、战役/存档标识、现实时间戳。
- 游戏日期、当前角色、暂停状态、窗口状态和客户区尺寸。
- 截图或截图引用、当前面板和弹窗信息。
- 当前任务需要的金币、收支、职位、婚姻、建筑或事件信息。
- 各字段的来源、采样时间与有效性。

未知、不可见、过期与数值 0 必须区分。识别置信度仅作辅助，不能单靠模型自报高置信度判定事实成立。

发生日期推进、角色变化、页面切换、窗口变化、读档或弹窗时，使相应旧状态失效。视觉与日志冲突时重新观察，不能静默选择方便执行的一份数据。

### 6.2 决策与执行结果

决策至少包含：任务类型、目标、引用的观察 ID、前置条件、预期结果、超时和简短理由。

执行结果至少包含：`action_id`、状态、证据、错误码和是否允许重试。状态区分 `success`、`failed`、`unknown`、`cancelled`。

示例成功条件：

- 内阁任命：指定职位显示所选人物。
- 建筑入队：目标领地出现预期建筑施工状态；仅金币减少不足以证明成功。
- 婚约请求：请求已发出并出现相应待回应证据；对方接受属于后续结果。
- 事件选择：对应选项已提交，事件关闭或进入预期后续界面；不要求随机效果必定有利。

请求已执行但回执丢失时，先核查游戏状态，禁止直接再次发起花费资源或产生外交影响的操作。

## 7. 建议工具接口

以下是待实现的接口设计，不是现成 CK3 命令。具体签名可在实现时细化，但不得削弱执行边界和核验要求。

```text
get_game_state()
click_game(observation_id, x, y, button)
hover_game(observation_id, x, y)
scroll_game(observation_id, direction, amount)
drag_game(observation_id, start, end, duration_ms)
press_game_key(key, duration_ms)
set_game_paused(paused)
set_game_speed(speed)
advance_game_time(max_game_days, max_wall_seconds)
verify_action(action_id)
save_campaign(slot)
get_run_status()
emergency_stop()
```

接口约束：

- 坐标基于游戏客户区，绑定截图尺寸和观察 ID；过期或越界请求被拒绝。
- 输入前检查目标进程、窗口和焦点，键盘与组合键采用允许清单。
- `set_game_paused` 表示达到目标状态，不能不检查状态就盲按切换键。
- 时间推进同时限制游戏内天数与现实时间；期间持续检测弹窗、失焦和停止信号。
- 推进期间无法读取游戏日期时，停止推进并报告未知，不将其视为达到日期目标。
- 每个动作具有超时和取消检查；只允许一个执行者控制输入。
- `emergency_stop` 不排队等待模型或普通任务完成；优先通过独立本地停止通道触发。
- 原子接口之上提供内阁任命等可核验任务流程，避免模型每次从零组织长点击序列。

## 8. 运行循环与异常处理

建议状态流转：待机 → 观察 → 确认暂停 → 决策 → 执行 → 核验 → 记录 → 有限推进 → 重新观察。

启动时完成自检，再由用户显式开始。收到用户停止、达到预算、环境不匹配或发生不可恢复异常时进入停止状态。

建议初始规则：

- 同一目标遇到同类失败最多重试 2 次，每次重试前重新观察。
- 连续 3 个周期没有可解释的状态变化或任务进展，停止并保存诊断信息；正常等待请求回应不直接计为故障，但必须有等待期限。
- 未知弹窗、必要状态不确定、窗口失焦、游戏崩溃或模型输出不合法时，阻止后续输入。
- 模型超时可有限重试；游戏默认保持已确认暂停状态。
- 用户接管时取消排队动作，恢复需用户显式操作。

必须分别报告：输入是否已停止、按键是否已释放、游戏是否已确认暂停。失焦或游戏无响应时不能承诺游戏已暂停，也不能向其他窗口盲发暂停键。

重启后先对齐游戏日期、角色、存档及未完成动作。对结果未知的历史动作先核验，禁止自动重放。

## 9. 预算、日志和存档

### 9.1 预算

必须支持运行时长、模型调用次数和 Token 上限。费用上限依赖已配置价格及可获得的用量信息；不能获得准确账单时显示估算，不冒充真实结算金额。

每次调用前检查剩余预算，设置单次输出限制并为在途请求预留额度。没有有效运行上限时不得进入无人值守模式。预算数值由配置指定，不默认授权无限运行。

### 9.2 日志

每次运行保存配置摘要、版本、状态流转、决策简述、动作、结果、错误和消耗。关键动作保存前后截图；稳定无变化阶段不必无限保存重复截图。

不记录 API 密钥；密钥使用安全输入、操作系统凭据存储或运行时环境传入。截图默认限定游戏区域。日志提供容量或保留时间限制。

### 9.3 存档

原始测试存档保留独立副本。使用专用测试存档名称和轮换规则，不覆盖用户其他存档；保存完成须有证据，不能把点击保存按钮视为完成。

第一版允许人工读档恢复故障，但记录恢复原因。验收中的失败不能通过反复读档隐藏，战略失败不自动触发回档。

## 10. 测试场景与验收

以下数值作为建议开发基线。若环境实验表明不可达，必须先提出带证据的调整，不得在验收报告中自行降低标准。

### 10.1 固定场景

准备四类非铁人存档或可复现前置步骤：

1. 存在空缺职位和合法候选人的内阁任命场景。
2. 金币足够且存在可建建筑的建筑入队场景。
3. 存在合法候选人的婚约请求场景。
4. 已显示并列入支持清单的普通事件场景。

验收运行通过正常 UI 执行。模拟界面和日志可用于自动化测试，但不能替代真实 CK3 实测。若无法取得某类场景，应标为未验证。

### 10.2 单项任务

每类场景从基线重置运行 5 次，至少 4 次达到该类任务的成功条件。保留全部尝试，包括失败、未知与取消；报告样本量，不将小样本结果泛化为任意存档成功率。

### 10.3 连续运行

在预先声明的内政测试场景中连续运行至少 30 分钟，无人工输入，完成至少 10 个具有证据的决策闭环，覆盖至少 2 类支持任务，并让游戏日期累计推进至少 30 天。

不能通过一直暂停、反复读取状态、来回开关同一面板或重复无意义任务达到计数。测试场景应在启动前确认有足够合法任务和预算。

### 10.4 故障与停止

分别测试窗口失焦、未知弹窗、模型超时、状态过期和重复无进展。验证无越界输入、无盲目重复提交，并输出准确停止原因。

紧急停止建议要求：触发后 1 秒内停止新增自动输入并释放由 Agent 持有的按键；正在等待模型时也必须通过。游戏暂停是否成功单独记录，不纳入无条件保证。

测试停止后重新启动，确认不会重放未核验动作。验证预算到达阈值后不再启动新的模型请求或游戏任务。

### 10.5 证据要求

真实游戏实测、模拟测试、代码审查和未验证项分别列出。每项验收能定位到日志、截图、配置及存档标识。无法访问实际 Windows CK3 环境时，交付可运行原型和测试步骤，但不得宣称 MVP 已验收。

## 12. 后续里程碑

### 阶段 1：可靠操作 MVP

完成上述第一版范围与验收，优先解决误点、错误成功判定、卡死和停止失效。

### 阶段 2：内政与继承

扩大结构化状态覆盖，支持人物死亡、继承交接、角色与权限变化、财政和封臣管理。使用跨代测试存档验证记忆不会沿用旧统治者身份。

### 阶段 3：外交与战争

增加宣战条件、兵力与财政评估、军队操作、和平条件及战后处理。分别评估操作是否正确与战略结果是否有利。

### 阶段 4：长期自主战役

引入明确的目标判定器，例如由配置指定目标头衔和领地条件，而不是仅依据模型宣布“统一成功”。定义失败、游戏结束、预算耗尽和人工中断等终止状态。

评估持续游戏年数、人工介入次数、技术故障、策略结果与成本。允许正常战略失败，但不能将程序卡死解释为王朝失败。

## 14. 给开发执行者的指令
